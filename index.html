carmen: AI-written GPU kernels, proven by a judge

solo · 6 days to a real-model result

An LLM writes Metal kernels for Apple Silicon. A deterministic judge proves each one against a float64 answer key on hundreds of inputs, including secret ones it never sees, then races it against MLX. The winners go into a real model.

The model writes; it never grades. Every failure comes back with where and why, and only kernels that survive the secret inputs get timed.

What I learned

  • AI kernels don't beat hand-tuned code. They beat code nobody fused. Wins come where MLX runs several kernels; where Apple wrote one tuned kernel, it ties or loses.
  • A kernel that wins alone can lose inside a model. One scored 1.15× in the judge and made Qwen 18% slower: wrong shapes, weak baseline, one launch at a time. Now the judge runs at the model's real shapes against mx.compile.
  • Measuring honestly was harder than writing kernels. Running versions back to back instead of taking turns produced two wins that weren't real (+40% prefill, 1.09× decode). A browser in the background swung speed by ±27%.
  • Small models on a Mac are launch-bound. Qwen 0.5B could run at ~346 tok/s on an M4's memory bandwidth; stock MLX reaches 51%. The rest is hundreds of tiny kernel launches per word.

  • Fast/slow model sync. A fast model acts on screen while the main model is still writing its plan. I built the sync layer between them: it skips plan steps the fast model already did, drops plans made stale by its wrong steps, and checks every irreversible action (send, delete) against the task before it runs. Fastest end-to-end task went from 27 s to 19 s.
  • Long-horizon memory for multi-step tasks in creative and CAD apps. Every step that checks out is written to disk; only the current state stays in memory. Context stays small, and the agent can jump back to any earlier step without replaying the session.

Each step is saved once it checks out. Memory only holds where you are now, so going back is just loading a frame.
